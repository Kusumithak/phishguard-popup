## 1. Purpose

The URL layer sees only the address. The DOM layer inspects the structure of the loaded page (form destinations, password fields, resources, scripts) without reading input values or sending page content anywhere. Role 3 made this layer measurable: the original hand-set score was replaced as the source of truth by a vector of 37 raw features, so the fusion model (Role 1) can learn the weights instead of using hand-set points.

## 2. Method

- **One extractor for training and deployment.** The crawler injects the same `content.js` that ships in the extension, so training features and live features cannot drift apart.
- **Data collection.** Same-day phishing URLs from openphish were crawled with Playwright in an isolated sandbox over 1 day(s) (2026-11-25). The crawler never filled or submitted a form and blocked every non-GET request. Benign pages came from a harness of 61 login pages (global sites, Indian banks and government portals, and 4 college portals).
- **Cleaning.** Dead or blocked pages were dropped, then one row per registrable domain was kept. Domains seen with both labels: 0.
- **Features (37).** Structure (forms, password fields visible / hidden / stealth-hidden, cross-origin vs cross-site targets, null actions, hidden iframes); resources (external-resource ratio, external scripts, foreign favicon); links (null-link and external-link ratios); redirects (meta refresh, cross-site refresh); inline scripts (`eval`, `atob`, obfuscation, `document.write`); brand-versus-domain mismatch. Page text and input values are reduced to 0/1 flags or counts locally and never stored.
- **Split.** Time-based: newest 7 crawl days held out as the untouched test set. Only 1 crawl day(s) so far, so a 7-day held-out window is not yet possible; the split will be fixed once at least 8 days exist.

Dead or blocked rate: 5.0%. **The DOM set is much smaller than the URL set**, because phishing pages die within hours and each needs a live crawl. DOM-layer estimates therefore carry wide confidence intervals.

## 4. False-positive analysis (benign login pages)

| Version of the hand-set rules | Benign pages | Red-banner false positives |
|---|---|---|
| Original | [FILL: fp_before_n] | [FILL: fp_before_k] ([FILL: fp_before_rate]) |
| After fixes | 60 | 1 (1.7%) |

Three fixes followed from this analysis:
1. `hidden_password_field` fired on closed login modals and inactive login steps, including GitHub's login page, and on hidden inputs named like "passkey". It now fires only on deliberately invisible fields (opacity 0, off-screen, 1px).
2. A `javascript:` form action was read as a different origin, flagging single-page-app logins.
3. Remaining known false positive: a password form posting to a sibling subdomain (SSO). It is left to the learned model, which has a separate cross-site feature for it.

Trade-off: a kit that hides its password field with `display:none` is no longer caught by that rule.

## 5. What the new features add *(synthetic)*

On eight fictional fixtures (four phishing-style, four benign), the original hand-set rules raised a red banner on 2 of 4 phishing-style pages. One of the two that were missed has no form at all (obfuscated script plus cross-site meta refresh plus brand mismatch) and is visible only to the new features. This motivates learned weights but is **not** evidence of real-world accuracy.

## 7. Latency

DOM scan time: median 2.6 ms, p95 11.3 ms (n = 136), measured inside the page by the crawler.

## 8. Limitations

- Only inline scripts and same-origin iframes are readable; external script bodies and cross-origin frames are not.
- The brand list is small (about 27 brands) and the same-site test is an approximation of the Public Suffix List.
- Headless crawling misses kits that fingerprint bots or geo-block, so the phishing sample leans toward simpler kits. A fast meta refresh may navigate away before the scan.
- Legitimate sites hotlink CDNs and favicons, so those two features are weak alone.
- Small sample: results are indicative.

## 9. Ethics and safety

All phishing pages were visited only inside an isolated sandbox with no credentials; nothing was entered or submitted. HTML snapshots are kept private and are not committed. The extension itself never reads input values and never transmits page content.
